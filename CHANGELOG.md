## [Unreleased]

### Added

- An Insights tab on every restaurant, in both portals: how the menu is being read, how far readers get, and how fast the kitchen turns an order around, at whichever grain is asked for — daily, weekly, monthly or yearly, the grain in the URL so a report can be sent as a link. It counts dishes opened and AR sessions, dishes put in a cart, orders sent by a guest and orders taken by a waiter, and the average time from an order arriving to the kitchen accepting it and to it being served; a window's totals sit above the same figures bucket by bucket, and an empty bucket is a row of zeros because a quiet Tuesday is a finding. **Two of those were not recorded anywhere.** A cart lives in the guest's browser and most carts are never sent, so nothing knew the step between reading a menu and ordering: `CartAdd` now records it (migration `20260923030000_cart_adds`), written by the guest menu alone — a waiter's cart is not counted, because a staff order is counted as an order. And a dish view was only written when the AR button was pressed, which made "views" a count of AR launches: a view is now recorded when a guest opens a dish, on the sheet or its own page, with AR remaining the subset it always was (`components/menu/track.ts`, beacons that never block or break a menu). Both counts start from today; the figures before it are AR launches and orders only. The report's arithmetic is `lib/insights.ts`, tested: a total re-weights an average by the orders behind it rather than averaging the averages, an order that never reached a stage is left out of that stage's average instead of counted as a zero in it, a clock that ran backwards floors at zero, and a window starts on a bucket boundary — a month-grained window starting mid-month would have put half of October in a bucket labelled October and made a thirteenth one of the rest. The grouping is Postgres `date_trunc` in UTC in three queries merged onto the bucket list (the three tables have nothing to join on but time, and joining them multiplies rows), pinned against a real database by `tests/integration/insights.test.ts`, including the refusals: another restaurant's report, and a tablet or a waiter asking for the one they work in.

- The Tables tab works a table at a time as well as a room at a time: every card carries its own Print and Copy — one table added, one label torn, one link to paste into a message or a printer's artwork — and the header gains Export CSV beside what is now "Print all" (a header row then one row per table with its link, RFC 4180, with a BOM so a spreadsheet reads an accented name as UTF-8; `tablesCsv`, tested including a name carrying a comma and a quote). What goes on paper is the code and the table number and nothing else — no restaurant name, no "Scan for the menu": these are working labels, and a printer setting them properly takes the CSV or a copied link and sets the name in the restaurant's own type. The number stays, being the one thing that differs card to card and cannot be read off a code by eye. Printing one table hides the rest of the room the same way the sheet already hides the shell, so a single card comes out instead of a page with one code and a lot of white; both print paths go through one piece of state and one effect, because a button calling `print()` itself would open the dialog before React had hidden anything, and the state is cleared on `afterprint` rather than straight after the call.

- The Info tab carries every address the restaurant hands out, not just the diners' one: the public menu, the order tablet's board (`/kitchen/orders/<id>`) and the waiter app (`/waiter/<id>`), each with its own Open, Copy and Share. A restaurant opening for service sets up three devices, and the addresses were in three different places — one on Info, one a tab away on Orders, one nowhere at all, which left the waiter's phone to be told a uuid out loud. The device links are by id and the menu link by slug, so a rename breaks the tab nobody has open rather than the one left running on the pass (`lib/restaurant-links.ts`, tested). The QR section says what the code on it is not — one code for the whole restaurant — and carries a button to the Tables tab, where a code per table fills the table number in for the diner so an order never reaches the wrong one; it reads how many tables are set, and offers to set them when there are none. How many tables the room has is now asked wherever the codes are (`components/qr/table-count-dialog.tsx`, a dialog over the same `updateRestaurant` Settings saves with): on the Info tab beside the QR code, and on the Tables tab both in its empty state and beside Print, where it used to send the reader to Settings and back. The number still lives in Settings → General; this is the same field asked for at the moment it is needed. The tab is one column rather than two: a link row needs the width for its address and its three buttons, and the QR code beside three of them read as an afterthought — it now has a row of its own, larger, with what to do with it beside it. One `LinkRow` serves all of them and the Orders tab's board card, and both portals' Info pages are now the same screen over one loader (`loadRestaurantInfo`): duplication falls to 66 clones / 843 lines.

- A device signs in with a username, not an address (`User.username`, unique, migration `20260923010000_user_username`). An order tablet and a waiter have no mailbox, so asking them for an email was asking for a fiction: they are created with a name (3–32 characters, letters, digits, dot, dash and underscore, folded to lower case so a capital typed on a tablet is not a different account) and the address the row still needs is derived from it on `staff.invalid`, the domain reserved so it can never be routed. One lookup answers both kinds — `accountFor` matches an address or a username — and the sign-in form asks for whichever the portal uses, with the right keyboard and autocomplete.
- A waiter app, for the guest who would rather not order from their own phone (`UserRole.WAITER`, "Waiter", made on the People tab beside the order tablets; migrations `20260922230000_waiter_role` and `20260922230100_order_placed_by`). A waiter signs in at `/waiter/login` — password only, no second factor, a month-long session — and gets the room's tables, each saying what is already open on it and how long it has waited. Tapping a table opens that restaurant's live menu with one tap per dish and one button to send; the cart is kept per table, so a waiter can start one table, walk away and come back to it. A staff-placed order needs no phone (there is nobody to text) and records who took it (`Order.placedById`); a guest's order is unchanged and still requires one. **The roles are separated by what they may do, and it is tested**: `requireRestaurantAccess` refuses both a waiter and a tablet, so neither can touch a menu, a dish, the settings or the people of the restaurant they are assigned to; `requireBoardAccess` reads the orders (managers, tablets, waiters); `requireBoardAction` moves one along (everyone but a waiter — the kitchen says what has been made); `requireOrderingStaff` places one (everyone but a tablet — it cooks what comes in). `tests/integration/staff-roles.test.ts` pins each of those refusals against a real database.
- An order tablet is its own kind of account (`UserRole.KITCHEN`, shown everywhere as "Order tablet"; migration `20260922210000_kitchen_role`), created on a restaurant's People tab with a username and a password. It signs in at `/kitchen/login` with the password alone — never a second factor, and `setMfaEnabled` refuses to give it one, because nobody is standing at the tablet to read a code — and the session is kept for a month (`auth.ts` sets `maxAge` deliberately rather than leaving it to the library). It lands on `/kitchen/orders/<id>`, the same board the portals show but with no way back into one: a tablet on the pass is not a signed-in manager, so it is offered no portal link. **The guard boundary is the point**: `requireRestaurantAccess` (every management read and write) now refuses a KITCHEN role outright, and a new `requireBoardAccess` is the only guard it passes — so assigning a tablet to a restaurant can never grant a write to its menu, its dishes, its settings or its people. A super admin can create, re-password and delete tablets (`app/actions/kitchen-actions.ts`), each action refusing an account that is not a tablet, so a manager cannot be reached through that door. Role names are said once in `lib/roles.ts` and read from there, so no list shows `RESTAURANT_ADMIN` at a human again.
- The Orders tab is the restaurant's order record, and the kitchen board is a link on it. The tab (in the portal, `/{admin,manager}/restaurants/<id>/orders`) opens with a card carrying the tablet board's address — open it, copy it, or share it to whoever is holding the tablet — then the last hundred orders: the state each reached, when it was placed, taken on and served, how long the table waited before the kitchen started, how long the food took, and the total wait, with a click on any row opening the same details sheet the board uses (read-only: a record, not a job). The two moments behind those figures are stamped by the move that caused them (`Order.acceptedAt`, `Order.servedAt`, migration `20260922190000_order_timestamps`, which backfills `servedAt` from `updatedAt` for orders already served); `updatedAt` could not answer it, because it moves again on any later change. A stage that has not happened reads as a dash rather than a zero, and a clock that ran backwards reads 0 rather than a negative minute. The board itself gains a Served view (`GET /api/orders/board` takes `status`; finished orders read newest first — what did we just send out — while the ones being worked stay oldest first, and no calendar day is cut anywhere).
- The kitchen board (`/{admin,manager}/orders/<id>`, reached from the Orders tab, outside the portal shell so a tablet gets the whole screen): the restaurant's open orders in two lanes — waiting, being made — each its own sunk tray with its own heading bar and colour, so where a card sits *is* its state and the two are never read as one list. Each card carries the table at 28px, the wait coloured (grey, amber at six minutes, red at twelve), the first dishes with what the guest asked for, and one 64px button that moves it on (Start → Served); the card itself opens a details sheet with every line, the note for the kitchen, the total, a tap-to-call number and the rest of the moves. Cancel lives in that sheet behind a second tap, so a passing hand cannot throw an order away. The tablet can install it (a per-restaurant manifest at `/orders/manifest`, a service worker scoped to that portal's `/orders` that caches the shell and never the API — a cached order list would show a kitchen work it has already done) and hold its screen awake (Screen Wake Lock, re-taken when the page comes back). Staff take an order on, call it served or cancel it (`setOrderStatus`, `Order.status` NEW → ACCEPTED → DONE, cancel anything not yet served; a move that does not apply leaves the row alone and answers where it stands, so two tablets cannot disagree). The board polls `GET /api/orders/board` every five seconds, with an alert for an order that was not there on the last poll and a "Test sound" button, because a browser stays silent until the page has been touched. The alert is built with the Web Audio API rather than a file (nothing to download or cache, and it works offline): a rising major arpeggio (C6, E6, G6, C7) answered by a softer echo of its last three notes, three and a half seconds in all. Each note is a struck bell — a sine fundamental with two quieter partials and a long decay — and they ring into each other through one compressor, so it carries across a noisy kitchen without the overlaps clipping. The tune is data (`components/orders/chime-pattern.ts`) and its voice is `use-chime.ts`; a test pins the rise, the echo, the overlap that makes it a bell rather than a row of beeps, and a length between two and four seconds — long enough to hear from the pass, short enough not to become an alarm. A failed poll keeps the last orders on screen and says the board is offline rather than showing an empty room; a tablet that wakes polls at once. Both endpoints are the restaurant's own staff only (`requireRestaurantAccess`, read through the order's row, never the body). Tests: the status moves, the waiting clock and its tiers, the split into lanes, the item count, the two schemas, and on a real Postgres the board's scope, order and shape, the refusals (another restaurant, signed out, a bad query) and the status moves that do and do not apply.
- The order is confirmed to the guest by text, and a QR code per table fills their table number in for them. Checkout asks for a phone number (required, written however people write it and stored normalised: separators dropped, `00` read as `+`; `Order.phone`, never logged) and the confirmation goes out over Brevo's transactional SMS in the language the guest was reading (`lib/sms.ts`, `lib/order-message.ts`, `BREVO_API_KEY` + `BREVO_SMS_SENDER`). The account is not linked yet: with the pair unset nothing is sent, the order is still taken and the server logs `order: placed, confirmation not sent`; a refusal or a failed request is reported the same way, so a message can never fail an order. A restaurant says how many tables the room has (`Restaurant.tableCount`, Settings → General) and a new Tables tab in both portals prints one QR code per table, each opening the menu with its number (`?table=`); the order sheet then shows the table read-only instead of asking, so nothing is mistyped and no order reaches the wrong table. Migration `20260922170000_order_phone_and_tables` (orders placed before it keep an empty phone). Tests: the phone's shapes and the confirmation's wording, the Brevo client (unlinked, the payload it posts, a refusal and a network failure), the table URLs and counts, the endpoint's phone on a real Postgres, and the two refusals in the browser suite.
- Ordering from the public menu, per restaurant (`Restaurant.orderingEnabled`, off by default, a checkbox in Settings → General; migration `20260922130000_orders`). A guest adds a dish with the `+` at the end of a menu row or the stepper on the dish sheet and dish page, sees what is in the order in a bar at the foot of the menu, opens it, changes the quantities, leaves a note on any dish ("no onions", one note per dish, on the dish sheet or in the order), gives a table number (shown read-only, not asked for, when the table's own QR code carried it) and a phone number, plus an optional note for the whole order, and sends it; the sheet then shows the order number. The order lives in `localStorage` as ids, counts and notes only, one cart per restaurant, followed across tabs (`lib/cart.ts`, `components/menu/cart/use-cart.ts`), and a dish taken off the menu drops out of it; the row's `+` counts from the stored cart rather than the render's, so two quick taps add two. `POST /api/orders` is public and re-prices every line from the database, refuses a restaurant that is not taking orders (403) and a dish that is not its active menu (400), and numbers the order from `Restaurant.nextOrderNumber` (`Order` and `OrderLine`, the line's name, unit price and the guest's note copied at the time, so a later edit leaves the order as placed; migration `20260922150000_order_line_note`). Tests: the cart's rules and its storage, the money arithmetic, the order schema, the join to the menu's dishes (79 unit assertions), the endpoint on a real Postgres (pricing, numbering per restaurant, the two refusals), and the journey end to end with an axe scan of the order sheet (`e2e/ordering.spec.ts`). The tablet page the kitchen watches, and its notification, come next: the orders are already stored with their status.

### Security

- Setting a manager's password is no longer setting it to a password everyone knows. The reset control on the admin portal's manager list and user page sent the same hard-coded literal for every account and then announced it in an alert box, so every manager reset that way shared one password, readable by anyone who had ever seen the box or the source. - A password alone never opens a session: the credentials callback used to sign a user in when no emailed code was pending and the account had no authenticator, so the code was effectively optional. `completeSecondFactor` now refuses unless a pending emailed code matches or a TOTP secret verifies (`lib/sign-in-checks.ts`); `sendMail` reports the provider's refusal (an unverified domain, a bad key) as "nothing sent" instead of claiming a send.
